## Programmatic verification

- Local `npm run check` passed version tracking, lint, TypeScript, 90 tests, and the production build. `npm audit --omit=dev --audit-level=low` reported zero vulnerabilities. `npm run test:browser` passed 52 Chromium and mobile WebKit tests. GitHub CI passed those release gates on the merged PR.
- The post-cutover live synthetic suite passed every check and reported `cleanup: verified`. It created five generated accounts, a cookbook, household grocery item and meal plan, recipes, invitation, and tiny image, then removed them. It verified Keeper, Contributor, Family, unrelated, anonymous, and removed-member access; atomic recipe creation and Keeper edit; invitation acceptance/reuse/wrong recipient; deployed cookbook, recipe, grocery, and meal-plan pages; authorized photo delivery; denied direct Storage and media-route downloads; and denied anonymous access through a fresh legacy public image URL. It never used existing family content.
- An unauthenticated request to the production media route returned its matched route with `Cache-Control: private, no-store` and 404. The live suite verified an authorized member's 200 response and an unrelated user's 404.

## Remaining 1.0 decisions and limits

- **Billing and email delivery:** Database and browser tests cover Stripe webhook replay/atomicity and unauthorized billing access, and production Stripe keys/webhook configuration were inspected. A real test-mode checkout, cancellation, failed payment, and invitation email delivery were not exercised against live production. Do these with isolated test-mode integrations if those paths are required for the first paid launch; avoid creating charges on the live account.
- **Old media caches and signed capabilities:** Fresh synthetic legacy public URLs are denied. Previously cached real-family public bytes and previously issued signed original-file URLs were not tested or rotated, because the synthetic test deliberately avoided existing family content. Follow the cache/token cutover guidance in [LAUNCH_RUNBOOK.md](./LAUNCH_RUNBOOK.md) before claiming historic media exposure has been fully closed.
- **Recovery operations:** The SQL restore and separate object export prove an inexpensive manual backup path, but Storage object reimport, a full application-level restore, backup automation/frequency, and recovery timing have not been verified. No separate staging project or managed PITR is configured in this setup.
- **Monitoring and acceptance:** No operator alert was triggered end to end. The owner has already done iPhone and family review; any further independent pilot and launch acceptance belong to the owner. Record operational monitoring, support contact, and a manual backup cadence before calling this a stable 1.0 service.

The repaired production app is functionally sound under the synthetic role and core-flow checks above. The owner chose the 1.0.0 designation with the billing, recovery, cache, and monitoring limits above still recorded for follow-up.
