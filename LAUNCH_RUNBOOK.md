# Launch verification and recovery

Local gates do not verify deployed service configuration. Use a dedicated staging Supabase project, Stripe test mode, verified staging email sender, and synthetic data. Production inspection, migration application, deployment, and restore require the owner's explicit approval. Do not reuse production credentials or user recipes in staging.

## Repeatable checks

Run `npm ci`, `npm audit --omit=dev --audit-level=low`, `npm run version:check`, `npm run lint`, `npm test`, `npm run build`, and `npx playwright test`. Install browsers with `npx playwright install chromium webkit` once. The committed CI workflow runs these gates on pull requests and main. Configure branch protection to require the `quality` job before merging. Configure deployment promotion to require that commit's successful checks.

The browser suite exercises the production build on desktop Chromium and iPhone-sized WebKit: public navigation, email validation, anonymous private-route protection, production-only development route hiding, and unauthorized billing rejection. It never submits an email or creates backend data. WebKit emulation is additional evidence; perform the device checks below on a real iPhone.

Run `node scripts/release-preflight.mjs staging` against staging variables or `node scripts/release-preflight.mjs production` against the release environment. It validates presence, obvious placeholders, HTTPS origins, Stripe mode, and browser-exposed secret-like names without printing values or contacting services. It does not prove key validity or project isolation. Verify deployment environment values independently, including baked-in `NEXT_PUBLIC_*` values.

## Create isolated staging before launch

Staging is not currently provisioned. These are setup steps for the owner; the audit tools do not provision services or apply migrations automatically.

1. Create a separate hosted Supabase project and Vercel preview/staging project, with clearly distinct names and credentials. Never link the local CLI to production while preparing staging. Disable real billing and use only synthetic accounts and recipes. Create a dedicated Stripe test-mode webhook endpoint for the deployed staging URL.
2. Copy the variable names from `.env.local.example` into staging deployment settings. Set `APP_URL` and `NEXT_PUBLIC_SITE_URL` to the same stable staging HTTPS origin; use staging Supabase keys, Stripe test keys/price/signing secret, and a verified staging email sender. Configure the Supabase Send Email hook URL and signing secret, auth site URL, and exact staging callback/confirmation redirect allowlist. AI credentials can incur charges; configure a separate account/token or quota appropriate to staging.
3. Review migration compatibility first. Two pairs of legacy filenames share numeric prefixes (`026` and `027`), so do not run an unreviewed `supabase db push`. For a fresh project, run `npm run migrations:prepare`. This creates a temporary migration directory outside the repository, copies committed SQL files in lexicographic order with unique timestamp versions, and writes a manifest mapping each generated filename to its original name and SHA-256 checksum. Review and retain that manifest. Copy only the generated SQL files into an isolated CLI project’s `supabase/migrations/` directory, link only the new staging project, and review the dry-run migration plan before applying. Apply this ordered set through the Supabase CLI using staging credentials only; retain the applied history and manifest. Do not rewrite the committed or production-applied migration history. Existing production projects need a separate reconciliation of actual applied versions before any production migration command.
4. Deploy the reviewed branch to the isolated staging Vercel project with these staging settings. Rebuild after setting `NEXT_PUBLIC_*` variables because they are embedded in browser assets. Confirm development routes return 404. Run the preflight against the staging environment; verify the actual deployment values independently without copying secret values into issue reports.
5. Invite the synthetic role accounts, seed a synthetic cookbook through normal app flows, and complete the acceptance record below. Restrict staging visibility if needed while preserving externally reachable auth hooks and Stripe test webhook delivery. Record its stable URL and the exact reviewed commit.

## Staging acceptance record

Record date, commit, migration history, tester, device/browser, result, and evidence for every item. Store synthetic screenshots securely; avoid access tokens in traces or logs.

1. Create Keeper, Contributor, Family, unrelated user, and removed-member synthetic accounts, plus an anonymous session. Use two cookbooks with distinct content. Apply the entire migration chain to an empty staging database; record the actual applied history. Duplicate numeric migration prefixes require checking the migration runner's identifiers against existing history; never rename applied migrations without reconciling that history.
2. Test signup, sign-in code, Google login if enabled, sign-out, expired code, repeated code, canceled OAuth, session refresh, return paths, invite accept/expiration/reuse/wrong recipient, and welcome/invitation email delivery. Verify auth redirect allowlists and sender DNS/domain verification.
3. For each role, assert allowed and denied reads/writes across recipes, cookbook membership, invites, photos, originals, groceries, and meal plans. Test direct database and Storage requests with each user's credentials as well as UI visibility. Remove a member while they are signed in; verify fresh reads and photo requests are denied. Previously delivered or downloaded content cannot be recalled.
4. Create/edit/delete recipes; replace/delete images and originals; switch cookbooks; use favorites, groceries, and meal plans; test empty/error/loading/success states. Upload HEIC/phone photos, oversized images, renamed invalid files, and interrupted uploads. Explicit public shares must work anonymously, then fail after revocation.
5. Test offline downloads and account switching on a real iPhone Safari, including installed PWA, storage pressure, network loss, reconnect, and sign-out. Private offline data must not become visible to a different account. Exercise narrow screens, keyboard focus, dialogs, camera/photo picker, and slow connections.
6. Stripe test-mode purchase, cancel, failed payment, portal, duplicate event, failed-event replay, older event after newer event, and simultaneous deliveries. Inject a database write failure; assert the webhook returns an error and replay repairs entitlements. Verify staging webhook signing secret and production endpoint configuration separately.
7. Run concurrent pantry requests at and beyond allowance boundaries; assert total successes stay within the durable allowance, and provider failures follow documented refund/retry behavior. Test a large synthetic cookbook and concurrent mutations; record response times and failure rates with a release-specific acceptance threshold.
8. Trigger a synthetic application error and failed billing webhook; prove the responsible operator receives an alert and can locate sanitized evidence. Verify logs contain no recipe content, email codes, invite tokens, keys, or signing secrets.

## Backup restoration rehearsal

Before promotion, document the database recovery point objective, recovery time objective, backup schedule, retention, and responsible operator. Verify the current plan's backup/PITR capability. Database backups do not include Storage object bytes: maintain a separately protected object backup with matching object paths, metadata, and restore instructions.

Use an isolated restore project with outbound emails, webhooks, AI calls, and billing disabled. Restore a staging backup and Storage objects there. Apply only migrations appropriate to that backup's recorded history. Compare row counts and relationships, verify representative synthetic photo/original bytes and checksums, and rerun the permission matrix using restored synthetic accounts. Confirm private buckets remain private, RLS remains enabled, and revoked shares stay revoked. Measure elapsed restore time and the newest recovered data timestamp against the recovery objectives. Retain the restore evidence and failure remediation; a backup listing alone is not a restore proof.

## Promotion and rollback

This release requires the private-media, atomic-billing, permission-hardening, and atomic-recipe migrations alongside the new app. Apply the reconciled migration sequence before directing traffic to this build; older app builds that use public media URLs will no longer display private photos. A safe application rollback must retain the authorized media routes or keep the affected flows disabled. Never reopen buckets as a rollback shortcut.

Before launch, warm representative legacy public image URLs on staging, make the buckets private, then verify those same URLs reject anonymous requests from a fresh browser and through the edge. Confirm any old image optimizer cache entries cannot be served under the new configuration. If previously public bytes persist in an edge cache, follow the provider's cache invalidation procedure or rotate objects and update references under an approved migration. Previously downloaded browser copies cannot be recalled. [Supabase documents public-bucket access](https://supabase.com/docs/guides/storage/buckets/fundamentals) and [Storage CDN invalidation](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

The old app issued signed original-file download and upload URLs. Deploying the new authenticated routes stops minting them but does not revoke capabilities already issued by Supabase. Before opening traffic, inventory and rotate legacy attachment object names using a verified copy/checksum/delete procedure in the same recipe folder, preserving the filename suffix, and verify old URLs fail after provider cache invalidation. Block legacy signed upload endpoints during the cutover or wait until previously issued upload tokens expire and reconcile any late objects. Rehearse and approve this data-preserving cutover on staging; do not treat a code deployment alone as legacy-token revocation.

Record the approved commit, app version, migration sequence, immutable deployment identifier, pre-release backup reference, and on-call owner. Review database changes for compatibility with the prior application version before applying them. After approved staging verification and production approval, apply migrations using the project's established runner, deploy that verified commit, and verify sign-in, private image display, role protections, and billing health with designated synthetic production accounts.

If application health regresses, promote the recorded previous deployment and verify its compatibility with the migrated database. Do not blindly reverse migrations or overwrite the live database. Disable affected integrations if needed to stop repeated side effects. Use a separately approved restore plan for data loss, with an agreed recovery point and reconciliation of events received after the backup. Record incident timing, affected operations, and recovery evidence before reopening traffic.
